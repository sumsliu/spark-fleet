# SparkFleet：把多机 Spark 推理的坑，变成下一套集群的起点

我们把部署 DeepSeek V4.1 Flash 四机 TP4、GLM 5.3 八机 TP8 过程中积累的配置、优化方法、补丁和验收流程，整理成了开源项目 **SparkFleet**。

项目地址：**https://github.com/sumsliu/spark-fleet**

真正影响使用体验的，往往不是一个漂亮的 tokens/s 数字：长对话每轮重算十几万 token，热请求排在冷输入后面，工具调用格式不对，菜单里能选模型但实际不能用，都会让集群难以服务日常开发。

SparkFleet 希望把这些经验留下来，让下一位使用者有一条可以审阅、复现、回滚的路：

- 两套分别适配的 DeepSeek / GLM 部署参考，不把不同模型的内核、KV 和推测解码参数混用。
- 前缀缓存与并发预填充优化，以及未获得稳定收益的失败实验。
- 真实 API、工具、流式、取消和长输入检查，验收通过才进入网关目录。
- 成对测速、基线漂移检查和正确性门槛，把“局部快了”与“整轮真的快了”分清楚。
- 中英文入口、运维回滚文档和可直接提交复现结果的模板。

原集群的一个测试里，约 2.5 万 token 的重复输入在缓存修复后从约 10 秒降到 0.5 秒；另一个并发测试里，高命中请求首 token 从 40.63 秒降到 4.99 秒。这些是带条件的历史参考数据，项目中保留了代价和限制。我们没有把多路合计速度写成单路成绩，也没有声称单路已经达到 100 token/s。

当前发布是 **v0.1 Alpha**。专用 SM121 运行时和合法取得的权重仍需自行准备，新整理的控制器也需要在更多独立集群上验证。我们最欢迎的贡献，是一份别人能重跑的结果：成功、失败、性能回退，都有价值。

如果你也在用 Spark 做多机推理，欢迎来试用、提问题、补构建步骤、贡献长对话测试，或者一起测清楚 200G 网络到底在哪一层成为瓶颈。

**让每一次“部署成功”有请求作证，让每一次“更快”有数据可复现。**
